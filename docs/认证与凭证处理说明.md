# 认证与凭证处理说明

本文说明仓库中的认证组件、请求流程，以及密码、会话令牌、GitHub 令牌和千问 API Key 的处理方式。

## 1. 组件

| 组件 | 代码位置 | 职责 |
| --- | --- | --- |
| 浏览器客户端 | `public/dance/app.js` | 提交登录请求；后续请求自动携带同源 Cookie；写请求附带 `x-yz-csrf: 1` |
| HTTP 路由与安全头 | `server/server.js` | 区分管理员、教师和舞蹈会话；设置 Cookie；校验 CSRF、Origin、会话和首次改密状态 |
| 账号与会话服务 | `server/auth.js` | 密码散列与校验、登录限流、随机令牌、会话续期、退出和密码重置 |
| 舞蹈职责授权 | `server/dance/service.js` | 校验学生、舞蹈教师、风险复核教师及班级范围 |
| 部署账号初始化 | `server/dance/bootstrap.js` | 仅在显式启用时创建演示或正式初始化账号 |
| 模型密钥管理 | `server/models.js` | 使用主密钥加密 API Key；对外仅返回“已配置”和末四位 |
| SQLite 数据库 | `server/db.js` | 保存密码散列、会话令牌散列、角色资料、审计记录和加密后的模型密钥 |

## 2. 登录请求流程

```text
浏览器
  │ POST /api/dance/auth/login
  │ login + password + x-yz-csrf: 1
  ▼
server/server.js 路由
  │ 选择 dance scope，记录请求 IP
  ▼
server/auth.js
  │ 检查登录名/IP限流
  │ scrypt 校验密码散列
  │ 检查账号状态和入口权限
  │ 生成 32 字节随机会话令牌
  │ 数据库只保存 SHA-256(token)
  ▼
响应 Set-Cookie
  │ dance_session=<原始令牌>
  │ HttpOnly; SameSite=Strict; Path=/; Max-Age=7天
  │ HTTPS 部署时附加 Secure
  ▼
后续 /api/dance/* 请求
  │ 浏览器自动携带 Cookie
  │ 服务端散列 Cookie 后查找会话
  │ 检查过期、账号状态、scope、角色和班级权限
  ▼
业务处理
```

管理员和上游教师平台分别使用 `yz_a` 与 `yz_t` Cookie；舞蹈平台使用 `dance_session`。三类 Cookie 和数据库 session scope 分离，不能用教师会话访问管理员接口。

## 3. 密码处理

- 密码必须为 8—128 位，并同时包含字母和数字。
- 每个密码使用 16 字节随机盐和 scrypt 派生，参数为 `N=16384`、`r=8`、`p=1`、输出 64 字节。
- 数据库只保存算法、参数、盐和派生结果，不保存明文密码。
- 密码比较使用恒定时间比较函数。
- 管理员重置密码时生成一次性临时密码，并立即撤销该用户的全部会话。
- 账号被停用或角色被调整时，相关会话会被删除。

## 4. 会话令牌与请求保护

- 登录成功后生成 32 字节加密安全随机值，并以 base64url 形式放入 HttpOnly Cookie。
- 数据库只保存令牌的 SHA-256 散列；数据库泄露不会直接得到可用 Cookie。
- 会话按空闲时间滑动续期，但绝对有效期不超过 7 天。
- 登录名和来源 IP 在 15 分钟内连续失败 5 次后会被临时限制。当前计数保存在进程内，重启后清空。
- 所有非 GET API 请求必须带 `x-yz-csrf: 1`；如果有 Origin，必须与 Host 同源。
- Cookie 使用 `SameSite=Strict`；生产 HTTPS 环境必须设置 `YANZHI_SECURE_COOKIE=1` 以附加 `Secure`。
- 响应同时设置 CSP、`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff` 和同源 Referrer Policy。

## 5. 千问 API Key

1. 真实密钥只通过运行时 `DASHSCOPE_API_KEY` 或管理员后台进入服务端。
2. `YANZHI_MASTER_KEY` 提供 32 字节主密钥；未配置时本地数据目录生成权限为 `0600` 的 `master.key`。
3. 模型 API Key 使用 AES-256-GCM 和随机 12 字节 IV 加密后写入数据库。
4. 前端、配置列表、审计和导出不会返回明文或密文，仅返回是否已配置、密钥末四位和版本号。
5. 调用供应商前仅在服务端内存中解密，错误消息会遮盖疑似密钥内容。
6. `YANZHI_MASTER_KEY` 丢失后无法解密既有密钥，因此正式部署必须稳定保管并与数据备份分开保存。

曾经公开过的 API Key 不能继续使用，应在供应商控制台撤销并重新创建。

## 6. GitHub Actions 与镜像凭证

- `.github/workflows/container.yml` 在 `main` 推送、版本标签和手动触发时运行测试并构建镜像。
- 工作流使用 GitHub 自动提供的短期 `GITHUB_TOKEN` 登录 GHCR，只授予 `contents: read` 和 `packages: write`。
- 千问 API Key、正式账号密码和主密钥不参与镜像构建，也不能保存到 Actions 日志或仓库文件。
- 镜像包含应用代码和变量占位符；运行时由服务器环境变量或部署平台 Secret 注入真实值。
- PR 只运行测试，不推送镜像；`main` 和版本标签才发布到 `ghcr.io/<owner>/<repo>`。

## 7. 需要运维侧保证的事项

- 公网部署使用 HTTPS，并开启 Secure Cookie。
- 关闭 `DANCE_DEMO_MODE`，为不同人员建立独立账号。
- 不提交 `.env`、数据库、`master.key`、`.local/`、视频和运行数据。
- 定期轮换千问密钥、管理员密码和部署平台凭证。
- 备份数据卷时同时规划主密钥恢复，但不要把主密钥和数据库放在同一公开位置。
- 反向代理应限制请求体大小、启用访问日志脱敏并设置合理的连接超时。
